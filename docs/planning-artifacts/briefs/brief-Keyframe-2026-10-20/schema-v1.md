# Schema v1: Keyframe

The Tier 1 / Tier 2 contract referenced by `addendum.md` §Schema v1 and realized once in `src/domain/schema.py` (architecture spine AD-2). The reviewers' changes were approved Oct 21 and are applied below. The Thu Oct 22 review picked option A for decoy storage (§Decoy storage). The schema freezes Mon Oct 26; later changes go through `bmad-correct-course`. The post-freeze changes accepted in the correct-course record of 29 Oct 2026 (`docs/planning-artifacts/sprint-change-proposal-2026-10-29.md`, items 32, 33, B2, S1, I1 and the later Trickster bounds fix) are applied in the sections marked amended. The story mode the owner approved on 29 Oct 2026 (treasure-chest hints, evidence held back, photo areas and start photos) is applied in the sections marked "(amended 29 Oct 2026, story mode)".

## Fields

Ids are prefixed ULIDs assigned by server code only: `room_`, `pz_`, `ix_`, `te_` (spine AD-18). Pixel coordinates are in the space of the stored downscaled 1280 px JPEG unless a field says otherwise.

Room: `id`, `created`, `name` (optional string, at most 40 characters, set when a Demo room is seeded; absent on ordinary Builds; the UI falls back to the build time; resolves PRD Q12), `photos[]` (`hash` = sha256 of the stored downscaled JPEG bytes, `size`, downscaled and original paths; JPEG only), `interactables[]`, `puzzles[]`, `decoys[]` (`[{id: te_, puzzle: pz_, interactable: ix_, visible_attribute}]`, empty on the stored build Room; written only by `apply_edit` on an accepted `decoy` edit, into the session's Effective room), `provenance` (model ids, prompt hashes, stage timings, regeneration count, spend per stage, `applied_edits[]`: ids of accepted Trickster edits folded into a session's effective Room, empty on the stored build Room). No `profile_name`; no `exit_puzzle_id`.

Interactable: `id` (`ix_`, minted by the segment stage after mask selection), `label` (the noun phrase sent to SAM), `photo` (index into `photos[]` in upload order), `box` (`[x0, y0, x1, y1]` in pixels, converted from the vision call's 0 to 1000 grid at segment time), `polygons` (list of polygons `[[x, y], ...]`, one per instance; `null` only before the segment stage completes; when SAM returns nothing the segment stage writes the box rectangle as the single polygon), `instances` (count when plurals are grouped), `attributes[]` (what the vision call reported, verbatim), `tier2` (optional GLB path and placement; the only field in original-photo pixels; pose from fal's metadata JSON if present, else hand-placed).

Puzzle: `id` (`pz_`; the Riddler emits ordinal keys `p1` to `p6`, mapped by the author stage), `lock_type` one of `code`, `order`, `use_on`, `find`; `requires[]` (puzzles that must be open first); `solution`, a tagged union by `lock_type`: `code` {`code`}, `order` {`interactables`: ordered `ix_` list}, `use_on` {`item`, `target`}, `find` {`target`}; `evidence` {`interactable`, `visible_attribute`}; `clue`; `lore` (at most 60 words); `rungs` {`nudge`, `direction`, `near_answer`}; `is_exit`. Four to six per room, exactly one with `is_exit: true`.

TricksterEdit: `id` (`te_`), `type` one of `decoy`, `merge`, `loosen`, `shortcut`; `puzzle`; `payload`, a tagged union by `type`; `validator_result` {`ok`, `reasons[]`}; `accepted`; `window`. Edits live in the session log as `trickster_card` events, server-side only, and never on the stored Room (spine AD-12); session state carries each card's `TricksterCard` projection (ids, type, outcome, reason and fixed message, no payload), never the edit (spine AD-3). Both outcomes render as cards.

Payload by type: `decoy`: {`interactable`, `visible_attribute`} adds a false evidence card for `puzzle`, which is never the exit puzzle (stored in `Room.decoys[]`, §Decoy storage); `merge`: {`puzzle_a`, `puzzle_b`} makes `puzzle_b` require `puzzle_a`, and the edit's `puzzle` is one of the two; `loosen`: {`puzzle`, `rung`} unlocks that rung immediately (applied to session state, not the Room); `shortcut`: {`puzzle`, `requires`} removes the existing edge from `puzzle` (the edit's own) to `requires`, and nothing else in the graph. Each payload also carries its `type`. Bounds come first: `validate_edit` refuses an edit outside the open window, naming a Puzzle, edge or rung that does not exist, putting a decoy on the exit or on a puzzle that already has one, or naming a Puzzle that is already open (`puzzle`, a merge's `puzzle_a` or `puzzle_b`, a shortcut's `requires`), since an edit there changes nothing the player sees. A bounds refusal is a reason with `rule: "edit_bounds"`, never a rule number, and the fixed message "The change is outside the Trickster's limits." Only then does re-validation run validator rules 1 to 8 and rule 9 on `apply_edit(room, edit)` (no dry run); either failure is shown as the rejected card and the effective Room is unchanged. The proposal prompt lists only the puzzles still locked; once every puzzle but the exit is open, a window makes no proposal call and appends no card.

API models, shapes defined in the architecture spine: `RoomDraft` (AD-7), `RoomView`, `PlayView`, `BuildView` and `TricksterCard` (AD-3; `TricksterCard` is `to_card_view` over a `trickster_card` event: `edit_id`, `accepted`, `edit_type`, `puzzle_id` (on a merge, the puzzle that now waits, `puzzle_b`), `related_puzzle_id`, `room_revision`, `reason` (null when accepted, the failing rule number or `edit_bounds` when rejected, `provider_unavailable` when skipped), `message`, `t_ms`, and no payload or content field; session state exposes `cards`, never a `TricksterEdit` or the event log), `ArchitectResponse` (AD-18), `DryRunAnswers` (AD-12, a list of `{puzzle_id, answer}` reusing the solution union, never a map), `RoomSummary` and `AccessCheck` (AD-9), `Derived` and `RoomResult` (AD-8), `Profile`, `SessionStart`, `ErrorEnvelope`, `Meta` (AD-15), the posted bodies and the event models (AD-4). `GET /schema` returns all of them.

Added after the freeze:

- `PlayPuzzle.sequence_length`: a required key, `int >= 1` for an `order` puzzle (its number of positions, one pip each) and null for the other lock types. It never carries the sequence or its objects; solutions stay server-only.
- `Profile` {`results`: map of room id to `RoomResult`, `derived`: `Derived`}: the browser's player profile, read and written by `GET|PUT /profile/<name>`, served in every Local app (never in Hosted mode). A result keyed under another room's id is refused, and the message names neither id.
- `SessionState.hint_reply`: `HintReply` {`puzzle_id` or null, `rung` 0 to 3, `text` exactly as shown, `next_hint_ms` or null}, set only on the reply to the `hint_request` it answers and never replayed. `rung` 0 is the No-hint line; `next_hint_ms` is the wait on the session clock until an ask opens that puzzle's next rung, null when none follows.
- `SessionState.trigger_events`: a map from log position (the values in `RungChangeEvent.triggered_by`) to `TriggerEvent` {`type`, `t_ms`}, one per event a `rung_changes[]` entry names, never its payload. It is served on top of the replayed state and never written by `apply`.
- `edit_bounds`: the named category in `ValidatorReason.rule` and `TricksterCard.reason` for a `validate_edit` refusal (payload paragraph above).
- `ErrorEnvelope` {`error`: `ErrorDetail` {`code`, `message`, `stage` or null, `status`}}: `status` is the job status, set only on `build_not_ready` and left out of every other answer. A 422 `invalid_request` or `invalid_profile` message names declared field paths only and never echoes a sent value, a key inside a dict field or a room id.

- `Room.story` and `PlayView.story` (amended 29 Oct 2026, story mode): a `Story` {`architect_welcome`, `trickster_trap`, `riddler_entrance`, `guide_chest`, `riddles[]` (`{puzzle_id, opening, solved}`, one per Puzzle, the exit last), `trickster_closing`, `riddler_closing`, `guide_closing_no_hints`, `guide_closing_hints`}, the wizards' lines the story stage writes once per Build (the storyteller's, or the fixed template lines filled from the Room); optional on `Room` and null on a Room built before story mode, so every stored Room still parses; `PlayView` always carries the key, null for such a Room. No line holds a solution token, a target or item label, an evidence attribute or a code. The storyteller's reply, `StoryResponse`, carries the same slots with `riddles` a list of `{opening, solved}` in riddle order and no map-typed field; it stays on the server, like the other model-response schemas.

`HintReply` and `TriggerEvent` are not listed models of their own; they reach `GET /schema` and `web/types` inside `SessionState`. (amended 29 Oct 2026, correct-course record)

## Story mode (amended 29 Oct 2026, story mode)

Owner decision 29 Oct 2026: a story intro, one riddle at a time, a treasure chest holding the Session's hints, and walking between photos. The contract changes:

- `Photo.area`: the room the photo shows, 1 to 24 characters, trimmed and lowercase ("front hall"); `Photo.pan`: its 0-based left-to-right order within that area, or null. A Room stored before story mode reads as area `"room"` and pan null. `PhotoView` carries both.
- `ArchitectResponse.photos`: a list (never a map, AD-2) of `ArchitectPhoto` {`photo`, `area`, `pan`}, one per photo; the Architect prompt asks it to name the room each photo shows in 1 to 3 plain words, the same words for the same room, and to order each room's photos left to right as if turning on the spot. The segment stage checks it (every photo named once, at most 4 areas, each label trimmed and lowercased to 1 to 24 characters, each pan 0 or more; a pipeline check, not a Validator rule) and copies it onto `Room.photos`; on any failure every photo gets area `"room"` and pan null, one ring in upload order. A reply stored before story mode has an empty list.
- `PlayPuzzle.start_photo`: the photo index the riddle starts on: its `solution.target` for `find` and `use_on`, its real evidence's interactable for `code` and `order`. It reveals a photo, never an object or a token; the solution still never leaves the server.
- `PlayPuzzle.evidence_cards` is held back: `GET /rooms/<room_id>` serves it empty for every puzzle, and `GET /sessions/<id>/room` serves it empty for every puzzle not in that Session's `locks_open` and the real card alone, never a decoy, once its lock is open.
- `SessionState.hints_left` and `HintReply.hints_left`: the chest's hints left, the Session's cap (`HINT_CAP`, default 2) less each Rung a `hint_request` opened, never below 0, replayed from the log. Under `HINT_POLICY=chest` (the default) only an asked Rung opens, the next one at once with no spacing; a `hint_request` with none left is refused 409 `hint_cap_reached`, message "The chest is empty.", with nothing appended; one that opens no Rung (the near-answer already open, or no puzzle active) is answered with the No-hint line "A fair ask. That one is all I had for this riddle; look once more." and spends nothing. `HintReply.next_hint_ms` stays and is deprecated: under the chest it is 0 while a hint is left and a Rung follows, else null. The Session's policy and cap are fixed at its start and kept beside its log; a Session stored before story mode replays under `ladder`, the earlier behaviour.
- Under the chest `validate_edit` refuses a `loosen` ("Hints come only from the chest.") and a `decoy` ("Evidence is hidden until a lock opens."), each an `edit_bounds` reason; `merge` and `shortcut` are unchanged.

## Lock input and inventory

`code` is typed into the lock's field; `order` is judged against the hotspot clicks made after the player starts the sequence from the puzzle's entry in the Wizard notes (event shape in spine AD-4): `order_start` is a lock input, so it makes its puzzle the Active puzzle and arms the buffer, which is armed only while its puzzle is the Active puzzle; while armed, every hotspot click fills the buffer; a full-length mismatch is one wrong attempt on the armed puzzle, which is the Active puzzle, and clears the buffer, which stays armed; stopping the sequence disarms it with no wrong attempt; whenever the Active puzzle changes to a different puzzle (a lock input on another puzzle, a hint request naming another available puzzle, a merge hiding the armed puzzle, or the armed puzzle opening) the buffer is disarmed and cleared with no wrong attempt and the player re-arms with "Start the sequence"; clicks while unarmed are exploration and never count; `find` is a click on the target hotspot made while no order sequence is armed (an armed click belongs only to the order attempt and never also opens a `find` lock); `use_on` drags an inventory item onto the target hotspot, or selects the item and then clicks the target (keyboard and alternative to drag); both send the same `use_on` {`item`, `target`} input with no puzzle id, and the server resolves the puzzle from the pair. Inventory: solving a `find` puzzle moves its target into the inventory only when a `use_on` puzzle of the Effective room names that interactable as its `item`; any other target is found, not carried: its lock opens and nothing enters the inventory. The rule is applied after every event, an accepted Trickster edit included, so every open `find` target a `use_on` names is held, in the order its lock opened, and nothing held leaves. `use_on.item` must be an interactable carried from a `find` puzzle listed in `requires` (validator rule 8). (amended 29 Oct 2026, correct-course record)

## Validator rules

All deterministic. Rules 1 to 8 gate the stored build Room; a Trickster edit is re-validated with rules 1 to 9. Reasons are structured `{rule, puzzle_id, field}` with a fixed message per rule and never quote an offending token or an answer (spine AD-3).

1. `requires` forms a DAG.
2. Every puzzle is reachable from the puzzles with no prerequisites; the exit is reachable from every other puzzle.
3. Every interactable named by a solution, evidence, or `use_on` pair exists.
4. `evidence.visible_attribute` appears, case-folded, in the attributes the vision call reported for that interactable.
5. No rung, `clue`, or `evidence.visible_attribute` may contain a solution token except as allowed below. Solution tokens per lock type: `code`: the code string and each of its digits; `order`: the labels of the listed interactables in that sequence (a rung may name at most one of them); `use_on`: the two labels together in one rung (a rung may name one, never both); `find`: the label of the target interactable. `nudge`, `direction`, `clue`, and `evidence.visible_attribute` contain no solution token; every displayed attribute says where to look and never holds a solution token; `near_answer` follows the per-type allowance above; `near_answer` is also checked against `clue`. Matching is case-folded. Code strings and each of their digits match as exact whole tokens regardless of length; for label words, only whole words longer than three characters match.
6. `lore` is 60 words or fewer; the three rungs are non-empty and increase in length.
7. Exactly one puzzle has `is_exit: true` (checked first); payloads are well-formed: `code` 3 to 6 characters, `order` 3 to 5 ids, `use_on` two distinct ids, `find` one.
8. Every `use_on.item` is the interactable of a `find` puzzle listed in that puzzle's `requires`.
9. A `decoy` names an interactable that exists; its `visible_attribute` is one the vision call reported for that interactable; the pair differs from every puzzle's real `evidence`; the target puzzle is not the exit; at most one decoy per puzzle; the attribute text contains no solution token under rule 5. Fixed message: "A false clue breaks the decoy rules."

## Dry run

A second `muse-spark-1.3` call receives the photos, the labels, every `clue`, and all three `rungs`, never the solutions, and returns `DryRunAnswers`, one answer per puzzle in the solution shape; `check_dry_run` compares them in the domain and a mismatch is a failure. Any failure regenerates the room with the structured failure reasons (never the previous draft) in the Riddler prompt; after 2 regenerations the build ends with status `needs_recapture`.

## SAM mask selection

One `sam-3.1` call per label on its clearest photo; selection runs in `domain/masks.py`. The mask with the best IoU against the vision box is kept; for a plural label ("books") every mask with IoU above 0.2 is grouped as instances of one interactable, falling back to the best mask when none passes; a mask is dropped only when it is under 1% of the frame and under 0.1 of its own box's area (`min_area = min(0.01 × frame area, 0.1 × box area)`), so a small object such as a floor vent keeps its outline; when no mask survives, the box rectangle is the single polygon; the room is capped at 12 interactables, highest vision confidence first. Polygons come from `meta-sam-parser`'s SVG path, scaled from the mask raster to the frame and simplified. [ASSUMPTION] Minimum: if fewer than 5 survive, the build ends with status `needs_more_photos` before any Riddler call, since four to six puzzles need that many distinct objects. (amended 29 Oct 2026, correct-course record)

## Decoy storage (picked Thu Oct 22: option A)

An accepted `decoy` edit lives in `Room.decoys[]`: `[{id: te_, puzzle: pz_, interactable: ix_, visible_attribute}]`, empty on the stored build Room and written only by `apply_edit` into the session's Effective room, so each `decoys[].id` is an accepted edit id listed in `provenance.applied_edits`. Rule 9 runs inside `validate(apply_edit(room, edit))` like every other edit check. `to_play_view` merges each puzzle's real `evidence` and its decoys into one unflagged `evidence_cards` list in a stable order seeded by the room id, so `PlayView` never marks which card is false and carries no `decoys` key. Story mode replaces that merge (amended 29 Oct 2026, story mode): `evidence_cards` is empty until the puzzle's lock is open and then holds the real card alone, so no decoy is ever served, and under the default chest policy no decoy is accepted. One test asserts decoy and real cards are indistinguishable in `PlayView` and in the serialized session responses (the `TricksterCard` projection carries no payload). A was picked over B (a decoy flag on the evidence list that every consumer must strip, the same class of leak as a solution) and C (cards defined in two places, the Room and the session log) because it leaves `evidence`, the Riddler schema, rules 1 to 8 and both views untouched except for one merge, and keeps AD-12 as written.
