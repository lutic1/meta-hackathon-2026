# Spine Pair Review — Keyframe

## Overall verdict
The pair works as a contract: a consumer can extract it cleanly. All 53 component names match one to one across `DESIGN.md` Components and `EXPERIENCE.md` Component Patterns. All 167 `{path.to.token}` references resolve, and all 33 contrast ratios in the table give the same result when recomputed from the frontmatter hex. Six of the seven UJs have a full Key Flow, and UJ-7 is a deliberate placeholder. Nothing blocks a build. The weak spots are bloat and a few contract gaps. `EXPERIENCE.md` restates architecture mechanics and repeats its own rules in up to five places, which is a drift risk. Four states have no defined home: network loss on the Capture screen, a refused session start, the modality of the Card log, and the Guide thinking state for an unrequested Rung. Twenty color tokens are aliases instead of hex values.

## 1. Flow coverage — strong
Checked: every UJ in PRD §2.3 (UJ-1 to UJ-7) and every FR with a UI (EXPERIENCE.md Closure) against the Key Flows. UJ-1 to UJ-6 each have a named protagonist (Ana, Priya, Luis), numbered steps, a bold **Climax** beat that matches the PRD climax, and a Failure line that covers the PRD edge cases. That includes HEIC refusal, `needs_more_photos` and `needs_recapture` (UJ-1), the 5 s fallback and the Early ask (UJ-2), the skipped Card (UJ-3), the different browser (UJ-4), and the wrong Access code, `queued` and the 21st Build (UJ-5). UJ-7 is a placeholder, as PRD §10.2 requires. Every surface either maps to a flow or is a declared guard state (Closure, line 110).
### Findings
- None. (The Rung thinking-state gap in UJ-2 step 1 is listed under §7.)

## 2. Token completeness — adequate
Checked: every key in the DESIGN.md frontmatter (`colors`, `typography`, `rounded`, `spacing`, `elevation`, 53 `components`); all 148 `{...}` references in DESIGN.md and all 19 in EXPERIENCE.md (none unresolved); every hex in the prose against the frontmatter (only the two computed composites, `#0A0806` and `#D9C8A9`, are not tokens, and both are labelled ≈); and all 33 contrast rows, recomputed with WCAG relative luminance (every row matches to 0.01). Dark theme only, per the memlog, so light/dark pairs do not apply.
### Findings
- **medium** Twenty `colors` entries are references, not hex: `pending`, `pending-ink`, all seven `card-*`, the three `clue-card-*`, and `graph-node`, `graph-node-ink`, `graph-node-exit`, `graph-pass`, `graph-fail`, `graph-skipped` (DESIGN.md frontmatter, lines 50–51, 63–81). The spec types `colors` as hex strings (design-md-spec.md, Frontmatter tokens). A token pipeline that mirrors the frontmatter gets the string `'{colors.parchment}'` where it expects a color. *Fix:* write the resolved hex on each role token and keep the alias in a trailing comment, or move the role aliases into the `components` block, where references are allowed.
- **low** Two frontmatter keys are outside the spec's token table: the top-level `elevation` group (lines 185–190) and `fontStyle: italic` on `typography.lore` (line 119). *Fix:* add one line under Elevation & Depth and Typography saying these are deliberate extensions. Otherwise, fold the shadows into component tokens and state the italic in prose only.
- **low** Several load-bearing pairs pass but are missing from the contrast table (Colors › Contrast): `error-text` on `chrome-raised` (failed Stage list row on the dropzone tray, 7.33), `success` on `chrome-raised` (stage done, 7.80), `lamp` as the secondary-button label and border inside error and warning banners (7.49 on `error-surface`, 6.55 on `warning-surface`), and `lamp-strong` on `chrome` (hover, 10.86). *Fix:* add these rows so the table covers every pair the Components tables use.
- **low** The narrow-screen heading has two type tokens. Typography (line 680) assigns it `display-lg`, but the Narrow-screen message row (line 825) says `display-sm`. *Fix:* pick one and update the other line.

- **low** The Cut 2 placeholder adds "Open profile file" and "Save profile file" controls with their own plain line (EXPERIENCE.md Closure, line 108), but no DESIGN.md row or placement covers them. *Fix:* add one sentence to the Retention summary and Completion screen rows naming them as Secondary buttons, or mark the placeholder as copy-only.

## 4. State coverage — adequate
Checked: every IA surface for cold load, empty, pending, success, error, offline/reconnecting, focus and disabled (permission-denied does not apply: no camera, mic or notifications in v1). The Capture screen, Build job statuses, Greeting, Play screen, Completion, Build view and Hosted landing all have state tables. Guard states (Leave room confirmation, Narrow-screen message, Deleted Judge room notice, Server unreachable) are covered in Component Patterns.
### Findings
- **medium** The Capture screen has no network-loss state. Foundation says "losing the network shows the reconnecting state only" (line 29), but the reconnecting state and its status strip are defined only for the Play screen (Scene column, lines 337, 446). Nothing covers a failed `POST /builds` upload (other than the 422 downscale refusal) or missed `GET /builds/<job_id>` polls during a Build: where the strip sits, whether the Timer keeps running, and whether the Stage list freezes. *Fix:* add a "Reconnecting (Build)" row to Capture State Patterns and an upload-failure row, and give the Status strip row a Capture placement.
- **medium** The "Session start refused" copy (Exact strings, line 239) has no surface. No state row says where a failed `POST /sessions` shows, what action it offers or where focus goes. It can fail after `done` on the Capture screen, after a Demo room card click on the Hosted landing, or after a stored Room "Play". *Fix:* add a row to Capture and Hosted landing State Patterns, for example an error banner with "Try again", with focus on the banner.
- **medium** The Card log's modality is ambiguous. DESIGN.md calls it a "Popover from the top bar" (line 796), but Elevation & Depth (line 720), Layout (line 711) and EXPERIENCE.md Demo Mode (line 607) put it under a scrim with the overlays. Navigation rules count it among the one-deep modals (line 73), yet Play State Patterns "Disabled" (line 448) lists only the Greeting and Leave room overlays as making Hotspots inert, and the Card log row (line 358) states no focus trap. *Fix:* declare it either a non-modal popover (no scrim, Scene stays live, no trap) or a modal (scrim token on `components.card-log`, focus trapped, Hotspots inert), and align the four passages.
- **low** Smaller state gaps:
  - No error state for `GET /rooms` on the Hosted landing or the stored Rooms list, and no empty state for zero Demo rooms.
  - No initial focus on the Build view.
  - No focus target after a Card is dismissed or after "Keep playing" closes the Leave room confirmation.
  - No open-but-empty Triggers panel state ("Triggers (0)").

  *Fix:* one row each in the relevant State Patterns tables.
- **low** The Hosted landing state row "Access code empty / checking / refused / accepted / quota reached" (line 473) leaves out "too many tries", which the Access-code build component row has (line 384). *Fix:* add it to the row.

## 6. Bloat & overspecification — thin
`EXPERIENCE.md` is about 107 KB over 672 lines, against reference examples of 5–9 KB. Most of the length is useful, but much of it restates the architecture spine or repeats itself inside the file. DESIGN.md prose carries editorial voice appropriately. EXPERIENCE.md prose stays neutral.
### Findings
- **medium** EXPERIENCE.md restates architecture mechanics and repeats its own rules across sections. Every architecture change would then need to be edited in several places, and the spine was already amended on Oct 21.
  - Restated architecture: event constructors (`LockInputEvent(CodeInput(puzzle_id, code))`, line 484), the `Meta` field list (line 605), AD-9 access-check semantics (line 384) and AD-3 projection contents (line 618).
  - Order-buffer arming rules in three places: Component Patterns (line 350), Interaction Primitives (line 483) and DESIGN.md Order click progress (line 788).
  - Hint-request behavior in five places: Foundation, Component Patterns, Interaction Primitives, State Patterns and Accessibility Floor.
  - Mode differences twice: the Foundation table (lines 39–48) and Hosted Mode Differences (lines 625–639).
  - The Build view four times: IA, Component Patterns, State Patterns and the Build View section (lines 614–621).
  - Privacy copy twice: Voice and Tone (lines 296–304) and Privacy and Retention (lines 641–649).

  *Fix:* give each rule one home and cite it elsewhere ("see Interaction Primitives › Order click buffer"). Replace AD restatements with the AD id plus the one consequence the UI needs. Fold the Build View section into Component Patterns and State Patterns, and the Foundation mode table into Hosted Mode Differences.
- **medium** DESIGN.md Components rows and Brand & Style carry behavior that EXPERIENCE.md owns.
  - Server semantics in Components rows: the Order click progress row says "every Hotspot click the server acknowledges fills the next pip" (line 788), and Access-code build (`POST /access/check`), Stored Room row (`GET /rooms`, AD-9) and Mode indicator (`GET /meta`) cite routes.
  - Brand & Style repeats the wizard-introduction placement (lines 569–576) and the register rule (lines 554–558), which EXPERIENCE.md Voice and Tone also specifies.

  *Fix:* keep visual anatomy and visual states in DESIGN.md, drop route and server references, and reduce the introduction placement to one pointer to EXPERIENCE.md Voice and Tone.
- **low** DESIGN.md writes pixel values next to the token that already holds them ("`{spacing.disclosure-min}` (32 px)", "`{spacing.side-column}` (400 px)", Layout & Spacing lines 692–697). It also specifies the Clue card slot twice: inside the Wizard notes row and in its own row (lines 780–781). *Fix:* drop the parenthetical values, and keep the slot spec only in its own row, with the Wizard notes row pointing to it.
