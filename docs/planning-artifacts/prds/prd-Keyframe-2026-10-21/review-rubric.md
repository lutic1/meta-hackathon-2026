# PRD Quality Review — Keyframe

## Overall verdict
This is a strong PRD. It has a clear thesis: your own room becomes a verified, cheat-proof puzzle chain with adaptive help and memory. The requirements are specific and mostly testable, the glossary is real, and the scope is honest, with tiers, a nightly cut order, gates that never move, and an assumptions index that matches the text. The risk is in the details that `bmad-ux` and story creation lean on hardest. The PRD never defines what "progress" means for Rung timing or which Puzzle a Rung is for. It does not say what a player sees when a Build fails, when a spend-capped call is refused, or after the near-answer when they are still stuck. It leaves the Greeting without a source in Hosted mode and under cut 3. All of these can be fixed in a few lines before the UX contract is drafted.

## Decision-readiness — adequate
Decisions are stated as decisions throughout. Tier 1 is "the floor, protected above everything" (§10.1). The cut order is fixed and ordered (§11.2). The Backup video gate is "never moved" (§11.1). The addendum's rejected-alternatives table (addendum §2) names what was given up and when to revisit it, which is unusually honest. Every Open Question in §13 is actually open and has a needed-by date (Q1 "Needed Thu Oct 22").

Two real tensions are left undecided and not flagged. First, the PRD never says what happens after the near-answer if the player is still stuck. FR-15 stops at three Rungs, FR-14 forbids anything above the current Rung, and no skip, reveal, or give-up exists. SM-2 ("a non-builder finishes room 1 ... without builder help") depends on this. So does any Room where the Architect misread an attribute (the mug's year read wrong) and the Dry run, seeing the same photo, agreed with the misread. Second, the Vision promises "The Guide's phrasing model runs on the player's own Mac" (§1), but Local mode is defined as "The product on Luis's M1" (§3). The only path for an outside player is Hosted mode, where no Guide model runs. Whether anyone else can run Local mode from the public repo is never decided, and Impact is 30% of the score. There is only one `[NOTE FOR PM]` (§10.2, Tier 2), so these tensions go uncalled.

### Findings
- **high** Stuck after the near-answer is undecided (§4.4 FR-15, §4.3 FR-14, §12 SM-2). Nothing defines the player's options once all three Rungs are used and the lock is still shut. *Fix:* Add a decision to FR-15. One option is: "After the near-answer, a further 3 Wrong attempts or one more stall shows a fixed 'ask the Riddler to reveal' control. Using it opens the lock, logs a `reveal` event, and counts as Rungs used = 4 in the Room result." The other is to state `[NON-GOAL for MVP] no reveal; a Room with an unsolvable misread is accepted risk, mitigated by the Dry run`. Either way, add a `[NOTE FOR PM]` naming the risk to SM-2.
- **medium** Who can run Local mode is undecided (§1 Vision, §3 Local mode, §9). The Vision's privacy and local-Guide claims reach an audience of one unless self-hosting is in scope. *Fix:* Add one line to §9 or §10. Either "`[NON-GOAL for MVP]` Self-hosted Local mode for other players; the README documents setup best-effort", or a new FR: "A player with a 16 GB Apple Silicon Mac, an API key, and Ollama can run Local mode from the README in under 15 minutes."
- **medium** UJ-6 contradicts FR-21 and FR-22 (§2.3 UJ-6 entry state, §4.6 FR-21, FR-22). UJ-6's entry state says "fresh Player profiles", yet the Main demo includes the room-2 Greeting. A room 1 played at the 6x Demo timescale would be flagged as demo by FR-22 and dropped from the Derived block, so the Greeting would have nothing to cite. *Fix:* Change the UJ-6 entry state to "`PROFILE=demo` holding one room-1 Room result played at Demo timescale 1; fresh profiles for the Capture proof." Add to FR-21: "Room 1 for the Main demo is played at timescale 1."

## Substance over theater — strong
Nothing here is furniture. The Vision could not move to another PRD unchanged: "the code is the year printed on their mug, the last lock opens on their bookshelf" (§1). There are two personas plus the builder, and each drives requirements: Priya's ten minutes drive FR-31 to FR-33, and Ana's return drives FR-20 to FR-22. The NFRs carry product-specific thresholds (NFR-3 "Guide model near 3 GB resident"; NFR-9 per-model RPM). Why Now (§1a) names a concrete enabling change and a forcing deadline.

### Findings
- **low** SM-5 and an FR-21 consequence measure which room Luis photographs, not something the product does (§4.6 FR-21, §12 SM-5). "At least 80% of room-2 Clues reference Interactables absent from room 1" cannot be enforced, because by design the Riddler never sees room 1 (the Derived block names no objects). It holds only because room 2 is a different physical room. *Fix:* Move it out of FR-21 into the delivery plan as a demo-setup check ("room 2 is a different physical room; at least 80% of its Interactable labels differ from room 1's"). Restate SM-5 as a validation of room choice, or drop it.

## Strategic coherence — strong
The thesis is explicit and the features follow it: capture (§4.1) feeds verification (§4.2), integrity holds through play (§4.3), adaptive help (§4.4) and memory (§4.6) make it a product, and the Trickster (§4.5) shows the rules bind the game too. The primary SMs validate the thesis rather than activity: SM-1 tests the capture claim, SM-2 that a stranger can play, SM-3 integrity. The counter-metrics are paired, and SM-C2 ("do not raise completion by giving Rungs sooner than FR-15 allows") is exactly the right guard. The MVP is an experience-kind scope with matching logic, and the tiers protect the one demo that matters.

### Findings
- **low** No SM checks the "recognize my own objects" emotional job (§2.1 Emotional, UJ-1 climax). SM-1 times capture and SM-2 tests completion, but nothing checks that Clues name real objects correctly, which is the Impact story. *Fix:* Add a secondary SM: "In the non-builder playtest, every Clue's Evidence attribute matches the physical object (checked by Luis against the room); zero misread attributes in Demo rooms."

## Done-ness clarity — adequate
Most FRs have testable consequences with numbers: FR-3's "masks under 1% of the image are dropped", FR-15's threshold formula, FR-24's "three Rungs arrive within 40 s". Several gaps sit exactly where stories will be cut. FR-15's "after the nudge threshold without progress" never defines progress. The spine defines idle as seconds since the last non-tick event, so any click resets it, and a player clicking around at random never gets a nudge; the PRD's word "progress" implies something else. FR-15 also never says which Puzzle a Rung belongs to when several are available. The spine resolves this ("the active puzzle ... is the puzzle of the most recent lock_input or attempted click"), but the PRD and glossary have no Active puzzle term. Build state `failed` appears in the glossary (§3 Build) but has no FR consequence and no message in §8. FR-28's "A refused call is surfaced to the player or Luis" says neither where nor how.

### Findings
- **high** "Progress" and the target Puzzle of a Rung are undefined (§4.4 FR-15, §2.3 UJ-2). Rung timing is the heart of the Guide, and the PRD wording ("without progress") contradicts the spine's mechanism (idle resets on any click). *Fix:* Add to §3: "**Active puzzle** — The Puzzle of the most recent lock input or attempted click; idle time and Hint requests apply to it." Add "**Idle** — Seconds since the last player event; any click resets it." Rewrite the first consequence of FR-15 as "The nudge for the Active puzzle fires after the nudge threshold of Idle ...". If clicking around should not count as progress, record that as a decision and send it back to the spine.
- **high** Failed Builds and refused calls have no player-facing behavior (§3 Build, §4.1 FR-5, §4.9 FR-28, §8 Capture screen). §8 lists messages for rejected formats, `needs_more_photos` and `needs_recapture`, but not `failed`. A Riddler call refused by the Spend cap, or a provider outage past the single retry (NFR-7), has no defined screen. *Fix:* Add a consequence to FR-5: "A Build ending `failed` (provider error after retry, Spend cap reached, or timeout) shows a plain message naming the cause class and a Retry control; no partial Room is playable." Rewrite FR-28's second consequence as "A refused call ends the Build `failed` with the message 'Spend limit reached for today' on the Capture screen; in play it shows a skipped Card (FR-19)." Add `failed` to the §8 message list.
- **medium** The Greeting has no source in Hosted mode or under cut 3, and persistence is undefined (§4.6 FR-21, §4.4 FR-17, §3 Derived block). The Greeting is "the Guide's opening line", but Hosted mode runs no Guide model and cut 3 removes Ollama phrasing. `persistence` also drives the threshold but is never defined in the PRD. Per `player-profile.md` it ranges from -1 to 1 and goes negative "when they ask early", which means a Hint request made before a Rung opens counts against the player. Neither the UX nor the stories can infer this. *Fix:* Add to FR-21: "Without a Guide model (Hosted mode, cut 3) the Greeting is a fixed template chosen by persistence band (below -0.3, -0.3 to 0.3, above 0.3)." Add to §3: "**Persistence** — -1 to 1; rises when the player keeps trying past the nudge threshold, falls when they make a Hint request before one." Add an FR-14 consequence: "A Hint request with no open Rung is recorded and lowers persistence."
- **low** Latency budgets have no percentile and no test environment (§4.1 FR-2 "within 15 s", FR-3 "within 10 s", §4.2 FR-7 "within 45 s", FR-9 "within 30 s"). NFR-8 makes story tests offline, so these numbers can only be checked against the live provider, and pass/fail is unclear. *Fix:* Add once to NFR-1: "Stage budgets are p50 over at least 5 live Builds measured Oct 27 to 28; over-budget stages log a warning and do not fail the Build." Then reference NFR-1 from each FR.
- **low** "Aligns with its object" is an adjective (§4.3 FR-11). *Fix:* "Each Hotspot polygon overlaps its Architect box at IoU ≥ 0.5 in image space (architecture spine AD-18)."

## Scope honesty — strong
Omissions are explicit. §2.2 Non-Users and §9 Non-Goals do real work. The cut table (§11.2) names the FR each cut changes. Tier 2 is "default no-go" with a `[NOTE FOR PM]` explaining what it costs emotionally. Every inference carries an `[ASSUMPTION A-n]` tag, and §14 matches. The open-items density is high for a green-light PRD: 8 Open Questions, 18 Assumptions, and 1 Note, about 27 in all. All seven User Journeys are unconfirmed (A-1 to A-7), and so are the Aesthetic (A-16) and the IA (A-17). Those last two are exactly what `bmad-ux` consumes first. This is not a blocker, since most are confirm-only, but they should be cleared before the UX run.

Two privacy omissions undercut the Privacy guarantees section (§4.13). FR-6's Retention summary names "the Meta Model API and, in Tier 2, fal.ai". In Hosted mode, though, judges' photos and originals are stored on Modal until Tue Nov 10 (FR-33). And voice (FR-35) sends audio to `muse-voice-transcribe-1.0`, with browser speech recognition as the fallback, which in Chrome means a Google service. That sits against FR-14's "Player text never travels to the server as text."

### Findings
- **medium** The Retention summary leaves out Modal storage and the voice paths (§4.1 FR-6, §6.1, §4.10 FR-33, §4.12 FR-35). *Fix:* Add to FR-6: "In Hosted mode the summary also states that photos, originals and the Room are stored on Modal until Tue Nov 10." Add to FR-35: "When voice ships, the Retention summary names `muse-voice-transcribe-1.0` and the browser's speech service; the transcript is reduced to a Hint request in the browser and never sent as text."
- **medium** No stance on accessibility (§5, §7 "Hotspots revealed on hover rather than outlined at rest", §9). Hover-only Hotspots hurt discoverability for a judge with ten minutes, and the PRD says nothing on keyboard play or colour contrast. *Fix:* Either add NFR-14, "Every Hotspot is reachable by Tab, with a visible focus outline; a 'show all hotspots' toggle exists; text meets WCAG AA contrast", or add to §9: "`[NON-GOAL for MVP]` Accessibility beyond Chrome defaults; hover reveal is kept for the Myst feel."
- **medium** Unconfirmed assumptions sit on the UX run's critical path (§14 A-1 to A-7, A-16, A-17). *Fix:* Before `bmad-ux` runs, confirm A-1 to A-7, A-16 and A-17 in one pass. Remove the tags that are confirmed and turn any that are rejected into `[NOTE FOR PM]`.

## Downstream usability — adequate
The glossary is thorough and used consistently. FR, UJ, SM and NFR IDs are contiguous, and FR-1 to FR-36 match `epics.md` FR1 to FR36 in meaning (verified). Each UJ has a "Capability → FR" line that resolves, and every UJ has a named protagonist. Mechanism is cited by AD number and doesn't leak into prose.

For `bmad-ux` specifically, the PRD under-specifies interaction feedback. It doesn't say what a player sees on a Wrong attempt, whether Puzzles whose prerequisites are unmet are visible (Wizard notes show "each available Puzzle", A-10), what a click on a Hotspot that is not a `find` target does, or what a Card for `merge`, `loosen` or `shortcut` says. Only `decoy` is defined in §3, though the schema defines all four. Several terms the FRs rely on are missing from the glossary: "nudge threshold", "Trickster window", "game-state summary" (FR-18), "scripted attack suite" (SM-3), "capture timer" (FR-24), and "status endpoint" (FR-26, the addendum's `GET /meta`). Reloading the page mid-Session is not covered for the player, although the Event log makes it possible.

### Findings
- **medium** Lock and Card feedback states are undefined (§4.3 FR-12, §4.5 FR-19, §3 Trickster, §8 Play screen). *Fix:* Add an FR-12 consequence: "A Wrong attempt shows a plain 'not this' state on the lock and the per-lock count; a click on a non-target Hotspot shows the Interactable's label only." Add an FR-11 consequence: "Puzzles with unmet prerequisites are hidden from Wizard notes." Add to §3: "`merge` — makes one Puzzle require another; `loosen` — opens the next Rung of one Puzzle immediately; `shortcut` — removes one prerequisite." Add to FR-19: "Each Card names the edit type and its effect in one plain sentence; a decoy Card never says which Evidence is false."
- **low** Several working terms are missing from the glossary (§4.4 FR-15 nudge threshold, §4.5 FR-18 game-state summary, §2.3 UJ-3 Trickster window, §12 SM-3 scripted attack suite, §4.8 FR-24 capture timer, FR-26 status endpoint). *Fix:* Add each to §3 with one line. Use "Timer" (T0 to T1) in place of "capture timer", and give the status endpoint its route.
- **low** Mid-Session reload is not covered as player behavior (§3 Event log "Session state replays from it", §4.3). *Fix:* Add an FR-11 consequence: "Reloading the Play screen restores the same Scene set, Inventory, open locks and current Rungs from the Event log."

## Shape fit — strong
This is a chain-top consumer game with a demo-driven audience, and the shape matches. The UJs are load-bearing, each mapped to FRs. A capability-spec spine of 37 FRs gives epic re-extraction a clean source. The Delivery Gates and Cut Order (§11) are unusual for a PRD but earn their place for a solo builder with a fixed deadline. The PRD is not over-formalized: UJ-6 for the builder is justified because the videos are a deliverable judged at 25%.

### Findings
- **low** Process and schedule leak into FR consequences (§4.6 FR-21 "A real room-1 record exists on `PROFILE=demo`", §4.9 FR-29 "committed with each build day's work", §4.7 FR-23 "(Thu Oct 29)"). Story extraction will turn these into stories with no product behavior. *Fix:* Move them to §11 as delivery checks, and leave each FR with only its observable system behavior ("Local mode writes a dated export at startup and after every Build").
